# Fabric Network Infrastructure

This directory contains the source-controlled infrastructure definition for the land tokenization Fabric network.

## What is committed
- Docker Compose source for orderers, peers, CAs, Explorer, and monitoring
- Fabric config source under `config/`
- Connection profile templates under `connection-profiles/`
- Operational scripts under `scripts/`

## What is intentionally not committed
- Generated MSP and TLS material under `organizations/`
- Generated channel artifacts under `channel-artifacts/`
- Runtime state, backups, logs, config dumps, and Explorer runtime data
- Local `.env` secrets

Those paths are ignored in `.gitignore` so the repo can be pushed safely to GitHub without leaking runtime state.

## Prerequisites
- Docker Engine with the Compose plugin
- A local `.env` file derived from `.env.example`
- Generated Fabric crypto material under `organizations/`
- Generated channel artifacts under `channel-artifacts/`

## Operational entry points
- `scripts/bootstrap.sh`: ensure the shared Docker network exists, render gossip TLS CA bundles, and start the core stack
- `scripts/networkStatus.sh`: show container and compose status
- `scripts/networkDown.sh`: stop the stack, optionally with `--volumes`
- `scripts/render-gossip-ca-bundles.sh`: rebuild deterministic cross-org gossip trust bundles
- `scripts/render-explorer-config.sh`: regenerate Explorer DB and Fabric connection config from the current network material

## Notes
- The peer gossip TLS trust is based on generated `combined-ca.crt` files inside each peer TLS directory. These files are regenerated by `scripts/render-gossip-ca-bundles.sh` and are ignored by git.
- The compose files now externalize credentials and admin passwords through `.env` variables instead of hard-coding defaults.
- This cleanup makes the repo publishable and materially safer to operate, but production readiness still depends on certificate lifecycle, backup/restore, secret management, HA testing, and deployment automation outside this directory.
